## 背景与动机

由于整个游戏的判断中会多次用到“视角”信息，我想要一个快速的，全局的“变量”，来存储当前的视角信息。
## 从GCS向GameplayTag同步ViewMode信息
### 选择GameplayTag存储当前视角信息

对于如何存储视角信息，有几种方案与各自的优缺点：

| 方案                        | 缺点       | 优点                     |
| ------------------------- | -------- | ---------------------- |
| PlayerController Variable | GA需要主动获取 | PC可以直接访问               |
| Subsystem Variable        | 繁琐，过度设计  | Singleton, Cross-Actor |
| ASC GameplayTag           | 随角色死亡消失  | GAS原生、GA获取零成本          |
对gameplaytag的选择简直是一个 no brainer。GameplayAbility可能是整个游戏中最频繁被调用的东西。任何能降低GA开销的因素都是deal breaker。于是我最终选择Gameplay Tag来存储视角信息：

- BaDaoZhan.Camera.Mode.TP
- BaDaoZhan.Camera.Mode.TD
- BaDaoZhan.Camera.Mode.Transition

其中TP和TD互斥，对应两种视角；Transition则独立地被维护，代表视角正在过渡。这种设置一方面和它们的意义与用途有关，一方面也和设置它们的方式有关，两者在下文中会更详细地解释。

### 使用BlueprintFunctionLibrary(+PC)维护GameplayTag
#### TD & TP

TD和TP分别代表俯视角和第三人称的视角状态，与激活的Camera Rig的种类相关。像UE设计理念上贯彻的“配置就该放在蓝图给策划用”的那般，切换CameraRig的逻辑在蓝图里，通过BlueprintCameraDirectorEvaluator调用ActivateCameraRig来唤醒。即使我认为这种重要的同步逻辑放在蓝图里十分的脆弱，十分“受制于人”，但出于对UE5的尊重（和更重要的，如果我要自己大改会很头疼），只好十分不情愿的把一部分同步放在BlueprintCameraDirectorEvaluator蓝图类里。但至少我能做到只让蓝图类调用一个函数，而不是直接在蓝图中写逻辑。为了做到这点，我需要包装“同步状态给tag”的逻辑。

BlueprintFunctionLibrary是为此而生的：它极少地在UObject上增加了一些“告诉大家它是函数库”的宏调用，在保证蓝图端使用便捷的前提下做到了最轻。于是，我添加BlueprintFunctionLibrary子类，在里面写了SetViewModeTag的静态函数。

- BaDaoZhan\Source\BaDaoZhan\AbilitySystem\BaDaoZhanAbilitySystemLibrary.h

``` cpp
UFUNCTION(BlueprintCallable, meta = (WorldContext = "WorldContextObject"),Category = "ViewMode")

static void SetViewModeTag(const UObject* WorldContextObject, ECameraViewMode NewViewMode);
```
	UBaDaoZhanAbilitySystemLibrary : public UBlueprintFunctionLibrary

其中meta=(WorldContext="WorldContextObject")的UFUNCTION metadata specifier 使蓝图自动传入WorldContextObject。蓝图用户只用选ECameraViewMode NewViewMode输入就能调用函数。好在蓝图中判断逻辑足够清晰，以至于还算清爽。

![](file-20260108120256067.png)

不同视角状态下会有不同的检测敌人模式，因此TD和TP tag应该互斥。为了保证tag不会stack，以及出于优化考虑（Get性能好于Set），需要在添加和移除tag之前判断是否已经有tag。

``` cpp
case ECameraViewMode::TD:  
    if (!ASC->HasMatchingGameplayTag(TD)){ASC->AddLooseGameplayTag(TD);}  
    if (ASC->HasMatchingGameplayTag(TP)){ASC->RemoveLooseGameplayTag(TP);}  
    break;  
case ECameraViewMode::TP:  
    if (!ASC->HasMatchingGameplayTag(TP)){ASC->AddLooseGameplayTag(TP);}  
    if (ASC->HasMatchingGameplayTag(TD)){ASC->RemoveLooseGameplayTag(TD);}  
    break;
```

##### 从LookAtBlend广播delegate
Transition tag的同步则更难一点。BlueprintCameraDirectorEvaluator里并没有途径判断现在是不是transition，它只知道“应该启用”哪个rig，实际的transition逻辑是在cpp中被处理的。那么，我们只能在blendnode里下手，在blend启用时Set Transition，在停用时Remove Transition。

在[25.12.10-25.12.24 消除视角跳变：基于逆向几何推导与二阶混合修正的 LookAtBlend 算法](25.12.10-25.12.24%20消除视角跳变：基于逆向几何推导与二阶混合修正的%20LookAtBlend%20算法.md)中，我写了LookAtBlend以达到丝滑的TP to TD摄像机过渡。但BlendNode是在引擎里的，而SetViewModeTag静态函数写在项目的library里。总不能让引擎依赖项目吧？

我想到的办法是，由LookAtBlendNodedelegate广播开始和结束，由项目中的PC监听，并相应地改ViewModeTag。引擎中提供了FGameplayCamerasDelegates容器，但我不想把只适用于一个blend的delegate放进去——容器里都是些很基础，很底层的delegate。于是，我选择只在LookAtNode头文件中声明Delegate，由PC依赖头文件获取delegate。由于LookAtBlend头文件保持得比较清爽，PC对它的依赖是可以接受的。

OnBlendResults中已经存在“第一帧”的判断逻辑，我还需要补上“最后一帧”的判断。阅读源码，发现blendstack在FTransientBlendStackCameraNodeEvaluator::InternalPostBlendExecute中，通过BlendNode的OutResult来决定是否终止Blend。

``` cpp

if (BlendResult.bIsBlendFull && BlendResult.bIsBlendFinished)  
{  
    PopEntriesBelow = ResolvedEntry.EntryIndex;  
}
```
	FTransientBlendStackCameraNodeEvaluator::InternalPostBlendExecute

先前，LookAtNode外层（BlendTimer控制旋转所属的部分）没有修改bIsBlendFull和bIsBlendFiniehsed，完全依赖内层simpleblend的进度。现在需要在最后一帧广播delegate，外层需要写结束的判断逻辑，正好可以将offset的blend进度添加至判断条件里。

###### Log诊断

观察Output Log。在从TP调用LookAtBlend到TD后（镜头停止移动时），会一直log如下的警告。再次调用LookAtBlend则警告消失。

	LogAbilitySystem: Warning: Attempted to remove tag: BaDaoZhan.Camera.Mode.Transition from tag count container, but it is not explicitly in the container!

Log显示，有人一直在尝试remove Transition tag，但Transition tag已经没了。整个项目里，我只在PC中监听LookAt的delegate，在广播时调用静态函数设置Transition tag。因此，这说明LookAtblend一直在broadcast delegate。

可是，OnBlendResults中能进行OnLookAtBlendFinished.Broadcast();说明bIsBlendFinished和bIsBlendFull为true。若二者都为true，上文提到的FTransientBlendStackCameraNodeEvaluator::InternalPostBlendExecute应该会获取当前ResolvedEntry的EntryIndex，加到PopEntriesBelow里踢出去。可是blendnode却“闹鬼”，还能继续broadcast。

在broadcast之前进行UE_LOG，输出bIsBLendFull, bIsActive和bIsBlendFinished。

``` cpp
void FLookAtBlendCameraNodeEvaluator::OnBlendResults(...)
{

	...
	
	if (OutResult.bIsBlendFull && !BlendTimer.bIsActive)
	OutResult.bIsBlendFinished = true;  
	else OutResult.bIsBlendFinished = false;
	  
	UE_LOG(LogTemp, Warning, TEXT("[LookAtBlend] FINAL: bIsBlendFull=%d, bIsActive=%d,bIsBlendFinished=%d"),OutResult.bIsBlendFull, BlendTimer.bIsActive, OutResult.bIsBlendFinished);
```

在编辑器中观察[Debug Log 1](Debug%20Log%201.md)，可以分成四个阶段：

1. 第一次activate LookAtBlend后，在blend进行的一秒钟内持续log：
	LogTemp: Warning: [LookAtBlend] FINAL: bIsBlendFull=0, bIsActive=1,bIsBlendFinished=0

2. 在第一次LookAtBlend结束后，先log一次：
	LogTemp: Warning: [LookAtBlend] FINAL: bIsBlendFull=1, bIsActive=0,bIsBlendFinished=1
并在直到第二次activate LookAtBlend前，持续log：
	LogTemp: Warning: [LookAtBlend] FINAL: bIsBlendFull=1, bIsActive=0,bIsBlendFinished=1
	LogAbilitySystem: Warning: Attempted to remove tag: BaDaoZhan.Camera.Mode.Transition from tag count container, but it is not explicitly in the container!

3. 第二次activate LookAtBlend后，在blend进行的一秒钟内持续log：
	LogTemp: Warning: [LookAtBlend] FINAL: bIsBlendFull=1, bIsActive=0,bIsBlendFinished=1
	LogAbilitySystem: Warning: Attempted to remove tag: BaDaoZhan.Camera.Mode.Transition from tag count container, but it is not explicitly in the container!

4. 在第二次LookAtBlend结束后，不再log。

其中1.十分合理。2.说明第一次 blend 完成后，bIsBlendFull和bIsBlendFinished都是true，OnBlendResults 仍然每帧被调用，广播 OnLookAtBlendFinished，尝试移除不存在的 tag。3. 说明第二次 activate 时，仍然使用上一个evaluator：bIsBlendFull, bIsActive和bIsBlendFinished还是上一个evaluator中的“完成”值，而不是1.中的“未完成”值。4.中不再log，说明evaluator真正被移除了。

这很诡异。疑点有二。其一是，为什么bIsBlendFull和bIsBlendFinished都为true后，LookAtBlend还没有终止。其二是，为什么1.2.和3.4.的表现不一致——3.4.的表现就像是第一个BlendNodeEvaluator直接被继续使用了，而非创造一个新的BlendNode一样。

我想第二点应该最先解决。种种迹象让我怀疑第二次activate的到底是不是LookAtBlend。直到我在FTransientBlendStackCameraNodeEvaluator::FindTransition中增加Log，查看要返回的Blend，才发现从TP到TD的Blend是LookAtBlend，而从TD到TP的是SmoothBlend。换言之，我的规则设立错误。

### Subsystem的诱惑

此时另一个选项变得更加诱惑了。除了能完美替代PC+FunctionLibrary的功能，subsystem是真正在运行的（一个单例），可以继承高贵的Tick，拓展性高。同时，继承于UObject，它也不重。

由于已经有PC，所以只用考虑function library和subsystem的开销与功能区别

| 需求    | BlueprintFunctionLibrary       | Subsystem               |
| ----- | ------------------------------ | ----------------------- |
| 全局可调用 | ✅ 静态函数，直接 UMyLib::Foo()        | ⚠️ 需要先 GetSubsystem<>() |
| 保存状态  | ❌ 只是函数容器，没有成员变量                | ✅ 天生就是用来存状态的            |
| 蓝图可调用 | ✅ UFUNCTION(BlueprintCallable) | ✅ 也可以                   |
| 轻量    | ✅ 没有实例，没有生命周期                  | ⚠️ 是 UObject，有初始化/销毁    |
最终没有选择subsystem的一大原因是，我没有用到额外的功能。在单人游戏中，Subsystem更多在角色死亡时存储信息用，像一个全局的存档点（或者，既然它的卖点是可以执行逻辑，更像Unity中的XXXManager）。它还可以每帧运行逻辑。事实上，如果想要的话，我们可以先在Subsystem里维护一套视角信息，再每帧向GameplayTag同步信息。但这些功能我都不需要，也自然不应该为这些额外的性能开销买单。

同时，从BlueprintCameraDirector蓝图类视角看：相比直接调用FunctionLibrary类里的静态函数，若使用Subsystem则需要先获取它的实例，再调用其中的函数，这会增加复杂度与新的依赖。虽然一个Subsystem能取代PC+FunctionLibrary在同步Tag里的角色，但对于例如Director的蓝图类来说，实际的依赖项从FunctionLibrary变成Subsystem，依赖反而增多了，架构更不灵活。还没享受Subsystem的便利，就“自损八百”，让我很难接受。

另一个原因是我不想架构过于抽象。计算机社区流传着一句话：过早的抽象是万恶之源。有考证的则是*Premature optimization is the root of all evil.*[^1] Opus 4.5也建议我保留原有架构，并如此评价：*当前方案工作正常、代码清晰、职责分明。Subsystem 虽然看起来”高级”，但在这个场景下只会增加复杂度而没有实际收益*。诚然，Subsystem的全局单例保留了世界上所有的便利之处，很有吸引力，但使用它们应该谨慎。否则，我的项目会像一个随机的Gamejam里的，一个随机的Unity作品一样，充斥着泛滥的xxxManager。愿上帝保佑我的个人项目，和我一月底将参加的GGJ HK的作品。
